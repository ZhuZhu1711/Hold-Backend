# 00 系统整体架构

面向懂技术的读者：本系统**做什么、数据从哪来、怎么落成 Hold Record、怎么流转到关闭**。接口字段与处置码细节见同目录 01–07 与 `docs/reference/`。

仓库：

| 目录 | 角色 |
| --- | --- |
| `Hold-Backend/` | Flask HTTP 服务 + 合批/采集调度 + Web 后台 |
| `FT-HoldSys/` | 工程师桌面客户端（PyQt） |

Oracle schema：`FT_OWEN`。生产 HTTP：`0.0.0.0:50001`（Waitress）；`--mode debug`：`60001`（Flask）。

---

## 1. 系统在解决什么

产线 Hold 事件从 MES 进来后，需要：

1. 把零散的 **hold_info**（按片、按码、按站）合成工程师能处置的 **hold_record**（一张异常反馈单）
2. 工程师查看测试图 / 缺陷，给出**处置意见**（放行 / 降级 / 重测 / 可靠性分析）
3. 生产侧按意见落地，必要时回退或关闭
4. 全程用 **circulation_history** 留下节点，而不是改写源 hold 事实

工程师处置**只写意见**：插入流转、回写 `STATUS` / `LAST_CIRCULATION_ID`，**不改** `FT_HOLD_RECORD.GRADE_NUM`。物理放行/降级/重测由生产执行。

## 2. 总体结构

```text
                    ┌──────────────┐     ┌──────────────────┐
   MES 产线 Hold ──►│ FT_HOLD_INFO │     │ 手提 / 外部 API  │
                    └──────┬───────┘     └────────┬─────────┘
                           │ 合批任务 ~30min      │ 直接插入
                           ▼                      ▼
                    ┌─────────────────────────────────────┐
                    │           FT_HOLD_RECORD            │
                    │  SOURCE=0 MES 合批 / SOURCE=1 手提  │
                    └─────────────────┬───────────────────┘
                                      │ DISPOSE=0 创建
                                      ▼
                    ┌─────────────────────────────────────┐
                    │        CIRCULATION_HISTORY          │
                    │  当前负责人 = 最新行 NEXT_OWNER_ID  │
                    └─────────────────┬───────────────────┘
                                      │
         ┌────────────────────────────┼────────────────────────────┐
         ▼                            ▼                            ▼
  工程师客户端/Web              生产 Web                       质量 Web
  ROLE=1 待办+分析+意见         ROLE=9 落地/回退/关闭          ROLE=8 只读报表
         │
         │ 研判数据（不写回 record）
         ▼
  TEST_WAFER / TEST_BINCODE / FT_WLT_TESTLOG(+FTP)
  MES DB Link（FVI 缺陷、合批源片）
```

调试与正式用**不同表**：`--mode debug` 读写 `FT_HOLD_INFO_TEST` / `FT_HOLD_RECORD_TEST` / `CIRCULATION_HISTORY_TEST`；release 用无 `_TEST` 后缀的正式表。客户端同样用 `--mode debug|release` 指向对应端口。

## 3. 角色与入口

| ROLE | 名称 | 入口 | 做什么 |
| --- | --- | --- | --- |
| `0` | root | `/admin/...` | 全量 Holding、合批失败、用户/型号 CRUD、报表 |
| `1` | 产品工程师 | 桌面客户端 + `/eng/...` | **仅** `PRODUCT_INFO.PRO_ENG_ID = 本人` 的型号；待办、分析、处置意见 |
| `8` | 质量 | `/qa/...` | 已处置物料只读报表，不参与决策 |
| `9` | 生产 | `/prod/...` | 生产节点 Hold：留样完成 / 回退 / 关闭 |

鉴权：Flask Session Cookie（`hold_session`），或外部系统 Header `X-Hold-Token`（匹配后跳过角色校验，操作人记为系统用户 ID=1）。无 JWT。

工程师主路径在桌面客户端（`FT-HoldSys/hold_client`）；Web 工程师页（`/eng/`）能力同源。生产与 root 主要走浏览器。

## 4. 核心对象

### 4.1 hold_info（源事件）

表：`FT_HOLD_INFO`（debug：`FT_HOLD_INFO_TEST`）。

**本系统不写入该表。** 行由 MES 侧插入（产线 Hold）。本系统只读、合批、回写关联字段。

关键列：

| 列 | 含义 |
| --- | --- |
| `HOLDING` | `0` = 仍在 hold（命名反直觉）；非 0 = MES 已解 hold |
| `HOLD_RECORD_ID` | `NULL/0` 待合批；`>0` 已挂到 record；`-1` 脏数据（不参与合批，需 root 处理） |
| `WAFER_ID` / `LOT_ID` / `HOLD_CODE` / `STATION` / `PRODUCT_ID` | 合批判定与分组键 |
| `GRADE_NUM` | 原始等级串，合批时合并进 record |

旧系统另有 `HOLD_INFO` / `WLT_HOLD_INFO` / `HISTORY_DISPOSITION`。新系统处置回写旧表默认关闭（`LEGACY_DISPOSE_WRITEBACK`）。

### 4.2 hold_record（处置单）

表：`FT_HOLD_RECORD`。一条 record = 一张可流转的异常反馈单。

| 列 | 含义 |
| --- | --- |
| `RECORD_TYPE` | `0` FT / `1` FVI / `2` WLT |
| `SOURCE` | `0` MES 合批；`1` 手提（无 hold_info） |
| `STATUS` | 与**最近一次处置码**同步；`99` 已关闭 |
| `LAST_CIRCULATION_ID` | 指向最新流转（留样完成 `65` 不改这个指针） |
| `WAFER_ID` | 单片 MES 片号，或合批展示串 `#01#02` |
| `HOLD_CODE` / `HOLD_REASON` | 多源用 `@` 拼接 |
| `HOLD_WAFER_ATTR` | 片属性比特位（真空包 / 各类合批），合批与手提写入时计算 |
| `ANNEX_FTP_PATH` | 手提/AQL 附件；多图 `@path1@path2` |

「在线」：

- MES：关联 hold_info 且仍有 `HOLDING=0`
- 手提：`SOURCE=1` 且 `STATUS <> 99`

合批任务**不再**按 `HOLDING` 自动关单。关闭走生产处置或手工脚本。

### 4.3 circulation_history（节点）

每一次动作一行。当前负责人 = 最新行的 `NEXT_OWNER_ID`（经 `LAST_CIRCULATION_ID` 关联，`65` 除外）。

创建时 `DISPOSE=0`，`NEXT_OWNER_ID` = `PRODUCT_INFO.PRO_ENG_ID`（找不到则系统用户 1）。

## 5. 数据从哪来

```text
MES 产线 ──insert──► FT_HOLD_INFO                    Hold 源事件
MES DB Link ────────► DEFECT_BIN_RELATION_H / LOT    FVI 缺陷明细
MES DB Link ────────► SPLIT_MERGE_HISTORY            FT 合批源片还原
ATE/WLT 机台 ──FTP──► /FT_TESTLOG / /WLT_TESTLOG     原始 testlog
本系统调度 ──解析──► FT_WLT_TESTLOG                  testlog 索引（路径+工步）
Raw CSV ──FTP──► /RAW_DATA/ ──独立进程──► TEST_WAFER + TEST_BINCODE
人工/外部 API ──────► FT_HOLD_RECORD (SOURCE=1)      手提 Hold（已下架）+ 历史附件
本系统 CRUD ────────► USERS / PRODUCT_INFO / FT_ENG_NOTES / SOFTWARE_INFO
```

| 数据 | 写入方 | 本系统用法 |
| --- | --- | --- |
| `FT_HOLD_INFO` | **MES（外部）** | 合批输入；在线过滤 |
| `FT_HOLD_RECORD` / `CIRCULATION_HISTORY` | 合批任务、处置接口（手提 API 已下架） | 业务主轴 |
| `FT_WLT_TESTLOG` | Web 进程内 Testlog 调度（release） | 定位最新 CSV/XML，再去 FTP 解析 bysite |
| `TEST_WAFER` / `TEST_BINCODE` | **独立进程** `FT_RAW_DATA_sche.py` | 分析页同 lot BIN / 良率 |
| FVI 缺陷 | MES `@MES16019` 实时查 | FVI 分析，不落本库 |
| 合批源片 | MES `SPLIT_MERGE_HISTORY` | FT 分片合批分析展开 |
| 手提附件 | 历史 `ANNEX_FTP_PATH`；上传/下载接口已关闭 | AQL_HOLD 不调 analysis |
| 型号工程师 | `PRODUCT_INFO.PRO_ENG_ID` | 创建时指定下一节点；工程师列表过滤 |
| 客户端版本 | `SOFTWARE_INFO.LATEST_VERSION` | release 下落后强制更新 |

Testlog FTP 与 Raw Data FTP、附件 FTP **不是同一台**。分析依赖 Testlog FTP 探活（`GET /api/common_data/ftp/status`）；挂了不阻断登录，但 bysite 会失败。

## 6. Hold 生命周期

```text
MES 插入 hold_info (HOLDING=0, HOLD_RECORD_ID=0)
        │
        ▼
合批调度（启动先跑一轮，之后每 HOLD_MERGE_INTERVAL_MINUTES，默认 30）
  1. 捞候选：HOLDING=0 且 HOLD_RECORD_ID∈{NULL,0}，且命中处置单划分
     本轮排除「HOLD_DTTM 最新那个 WAFER_ID」的全部行，避免 MES 同片多行未插完
  2. 再过滤：无 WAFER_ID / 不满足划分 / FPQC+025+FUTURE HOLD → 标 -1
  3. 分组：
       普通      (WAFER_ID, RECORD_TYPE)；FT 028 单独成桶
       分片合批  (LOT_ID, RECORD_TYPE) 当 LOT≠WAFER 且 lot 后缀数字>2 位
       WLT       (lot 前缀, RECORD_TYPE)，WAFER_ID 写成 #01#02
  4. 组内去重：(WAFER_ID, STATION, HOLD_CODE) + 1 小时时间窗，留最早
  5. 同一事务写入：
     - 梓一合批（ATTR bit1）：同 LOT + RECORD_TYPE + 028 分桶、且已有 MES record 的
       HOLD_DTTM 落在本轮最早 HOLD_DTTM 回看 HOLD_MERGE_INTERVAL_MINUTES（默认 30 分钟）内
       → 追加（不论 STATUS；更新 WAFER_ID / HOLD_CODE / HOLD_REASON / GRADE_NUM / HOLD_DTTM，
         回写新 info 的 HOLD_RECORD_ID；不插流转、不改 STATUS；多笔取最小 ID）
       超出回看窗口则新建（含仍为 STATUS=0 的旧单；用于重测后再 hold）
     - 其它：INSERT record + CIRCULATION(0) + 回写 hold_info.HOLD_RECORD_ID
     失败整单回滚，本轮源行标 -1
        │
        ▼
工程师待办（NEXT_OWNER = 型号工程师）
  可选：分析（bysite / BIN / FVI 缺陷 / AQL 附件）
  处置意见 1 放行 / 2 降级 / 3 重测 → NEXT = 生产 OP（默认 181）
  处置意见 5 可靠性分析 → NEXT 仍是自己；生产可并行 65 留样完成（不改节点）
        │
        ▼
生产节点
  8 回退 → 回到型号工程师
  99 关闭 → 终态，不可再处置
```

处置单划分（不满足则 **不成 record**）：

| RECORD_TYPE | 产品 | Hold 码 | 站点 |
| --- | --- | --- | --- |
| 0 FT | `*-3.5` | 023/024/025/027/028/AQL_HOLD | ∉ FAOIFINISH, FFVI（排除 AQL_HOLD + FAOI-BACK） |
| 1 FVI | * | 023，或 AQL_HOLD | 023 ∈ FAOIFINISH/FFVI；AQL_HOLD = FAOI-BACK |
| 2 WLT | `*-2.6` | 004/022 | WOQC |

第二条创建路径：**手提 Hold**（**已下架**，接口 410）。历史数据为 `SOURCE=1` 直接插 record，不写 hold_info、不合批。下架前 FT 仅 `AQL_HOLD`，WLT 为 004/022。

合批失败（`-1`）：root 页可重置为 `0` 等下一轮，或按选中行手动提 record。实现：`hold_merge_fail_ctrl.py`。

## 7. 处置意见 vs 生产落地

```text
系统创建 0
    → 工程师 1/2/3 ──► 生产 OP ──► 生产关闭 99
                 ↘ 工程师 5（自循环）──► 仅允许再 1/2（须手输备注）
                              生产可同时点 65 留样完成（只追加流转，不改 STATUS）
    → 生产 8 回退 ──► 工程师再处置
```

| DISPOSE | 谁发 | 效果 |
| --- | --- | --- |
| 0 | 系统 | 创建，NEXT=型号工程师 |
| 1/2/3 | 工程师 | 意见，NEXT=181 |
| 5 | 工程师 | 可靠性分析，NEXT=自己 |
| 7 | — | 转交，当前屏蔽 |
| 65 | 生产 | 留样完成，不改负责人/STATUS |
| 8 | 生产 | 回退工程师 |
| 99 | 生产/root | 关闭 |
| 6/66 | — | 已废弃，仅历史展示 |

WLT（`RECORD_TYPE=2`）必须按片提交 `wafer_actions`，覆盖该单全部片；记录级 STATUS 按片汇总（任一 5→5，否则任一 3→3，否则任一 2→2，否则 1）。FT/FVI 整单一次处置。

可处置条件（工程师）：未关闭 + 当前负责人是本人 + 型号归属。`CAN_DISPOSE=false` 仍可分析。

## 8. 分析数据怎么拼

分析**只读**，不改变 Hold 状态。入口按类型分流：

| 类型 | 接口 | 数据 |
| --- | --- | --- |
| FT / WLT | `GET /admin/hold/api/analysis` | FTP bysite（经 `FT_WLT_TESTLOG`）+ `TEST_WAFER`/`TEST_BINCODE` 同 lot BIN |
| FVI | `GET /eng/api/fvi_defect_details` | MES `DEFECT_BIN_RELATION_H` |
| `HOLD_CODE` 含 AQL_HOLD | 附件图接口已下架（410） | 不要调 analysis；附件 FTP 下载已关闭 |

`/api/analysis` 的 `station` 由客户端推导，不要传 Holding 行原始站点：

- FT 且 `LOT_ID` 含 `-` → `FATE-FA`
- FT 且不含 `-` → `VBOX-FA`
- WLT → `WLT2`

同 lot BIN 始终拉 WLT + FA 两站。FT 分片合批（lot 后缀数字 > 2 位）经 `SPLIT_MERGE_HISTORY` 展开源片。

## 9. 后台任务

挂在 `app/main.py` 的进程里：

| 任务 | 何时 | 做什么 |
| --- | --- | --- |
| `HoldMergeScheduler` | debug / release 都启 | hold_info → hold_record |
| `FlaskTaskScheduler`（Testlog） | **仅 release** | 扫 FTP 目录，索引写入 `FT_WLT_TESTLOG` |
| `HoldPredictScheduler` | release 且 `HOLD_PREDICT_ENABLED`（现默认 False） | FT 可放行概率静默打分，不改 UI |

独立进程（不挂 Web）：

```text
python app/backend_schedule/FT_RAW_DATA_sche.py --mode release
```

从 `/RAW_DATA/` 拉 CSV，写入 `TEST_WAFER` / `TEST_BINCODE`，默认约 60 分钟一轮。分析 BIN 依赖此进程，与合批无关。

合批也可单独跑：`python app/backend_schedule/FT_HOLD_MERGE_sche.py --mode debug`（一轮后退出）。

## 10. 工程师客户端最小闭环

实现：`FT-HoldSys/hold_client`。release 会对照 `SOFTWARE_INFO` 做版本卡控。

```text
登录 MD5(密码) → POST /api/login（role 必须=1）
  → 探活 FTP、查 latest_version
  → GET /eng/api/holding_records?pending_only=1
  → 分析（按 RECORD_TYPE / AQL 分流）
  → CAN_DISPOSE 时 GET /eng/api/records/{id} → POST /eng/api/dispose
  → 刷新列表（1/2/3 后通常离开本人待办）
```

生产处置客户端**不做**。
